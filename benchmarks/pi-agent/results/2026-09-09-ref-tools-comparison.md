# 增强后 bro 与 agent-browser：ref 工作流同场对比

日期：2026-09-09。24 个独立 Pi subagents；同一 Luna/max；6 场景 × 2 产品 × 2 轮。产品顺序交替，测试期间代码、编译产物及 skill 冻结。

**结论：bro 在深层 iframe 和旧 ref 错误信号上更可靠，但不是全面更快；后台滚动是本轮确认的 bro 短板。**

## 同场表

每格为 **平均秒数 / 平均模型工具调用 / 平均 processed tokens**。时长包括 skill 加载、模型推理及恢复。失败尝试也计入该格；240 秒是截止上限，不是完成耗时。

| 场景 | bro 通过 | bro 均值 | agent-browser 通过 | agent-browser 均值 |
|---|---:|---:|---:|---:|
| 三类 iframe 表单（含跨站嵌套） | 2/2 | 58.6s / 12.5 / 146.6K | 0/2 | 240.0s / 34 / 557.0K |
| 独立双层 Shadow DOM 表单 | 2/2 | 29.5s / 6 / 45.3K | 2/2 | 39.6s / 10.5 / 97.3K |
| 带 padding 的 14px iframe 按钮 | 2/2 | 29.5s / 6 / 51.4K | 2/2 | 43.2s / 11 / 107.1K |
| 旧 ref 拒绝＋新 ref 恢复 | 2/2 | 36.4s / 8 / 63.5K | 0/2 | 49.1s / 11.5 / 112.1K |

总体按任务契约通过：**bro 11/12，agent-browser 8/12**。这不是所有网页的成功率。

## 不要从总耗时推出统一倍数

全矩阵运行时长含失败和超时，不能拿来计算完成同等任务的速度倍数。只有 7 组同任务、同轮次的配对双方都通过：

| 双方通过的 7 组配对 | bro | agent-browser |
|---|---:|---:|
| 总时长（秒） | 297.054 | 285.056 |
| 模型工具调用 | 64 | 73 |
| Processed tokens | 604977 | 717395 |

bro 在这个子集里并没有更快：滚动恢复的长尾抵消了其他场景的收益。这个成功子集本身也有选择偏差，仍应优先看逐场景结果和失败原因。

## 验收与失败解释

### 嵌套 iframe
两个 agent-browser 运行都完成了 Same/Cross 两个表单，但在更深一层 frame/ref 定位中耗尽 240 秒。不能因此说它连普通 iframe 都不支持。bro 两轮完成；第二轮一次 Nested Commit 派发后没有出现应用事件，观察和等待后第二次点击才成功。未在本轮诊断或修复该残余问题。

### 旧 ref：成功返回不等于有作用
两轮 agent-browser 都正确保留并使用原 Editor ref，在 Replace editor 后、刷新 snapshot 前执行负向填写。CLI 均返回 Done/exit 0，但新输入框仍为空、WRONG_WRITES:0；随后用新 snapshot 正常恢复。这是**静默无效操作／错误信号不准确**，不是已证实覆盖了新节点。按要求“旧 ref 明确拒绝”的契约，两轮失败。bro 两轮明确拒绝，并恢复成功；这两次预期 tool error 不算意外故障。

### 滚动：bro 的实际短板
第一轮后台 flow 的可见状态停在 0，模型重复观察和滚动，最后重新打开前台 flow 才完成 100→920→920。第二轮 get_element_info 证实 offset 已到 100/920/920，但 AX、纯文本和输出元素本身长期仍显示 SCROLL_TOP:0；最后截图和日志出现了 920，**从未验证到可见的 100**。因此第二轮不通过，不能把内部 offset 推断成已看见的 UI 文本。

下一步应在滚动事件／渲染生命周期的 owner layer 修复，并新增“新建后台 tab”的回归；不能只加等待、改 prompt 或跳过 UI 验证。滚动尚未进入 ref-aware flow step，也增加了模型回合。

### 正常场景
Shadow DOM、14px padded iframe 按钮两边都通过，bro 的模型调用更少。上传两边均通过，时间区间重叠，不足以宣称稳定赢家。bro 第一轮上传多了一次 browserId="default" 参数错误，恢复耗时已计入。

## 公平性与限制

- 两边都是有界面的 Chrome for Testing 152.0.7977.82；每格开始前验证 1280×857、DPR 2；没有登录态复制。
- bro 是暖的 suite-owned 浏览器；agent-browser 每格预备独立命名浏览器 session。浏览器启动/准备不计时；产品本身的启动参数与前后台默认策略仍不同。页面本地、资源内联且 no-store。
- bro 使用正常十工具初始面和当前已安装官方 skill，不是此前的“四工具最短路径”验收配置。该 skill 的旧 iframe recipe 尚未随未发布实现更新；由新 schema 提供 ref-first 能力说明。
- agent-browser 使用 CLI＋匹配版本的官方 skill，未测试其原生 MCP 接入。
- 写操作只允许观察到的 refs；禁用 JS、坐标、CSS 写操作和外部 HTTP 客户端。纯读 frame 上下文选择允许使用各自原生接口。
- 可信点击是共同要求；input 事件数量不是通过条件，以免把“bro 的一次 setter”和其他合法输入实现强行等同。
- 两轮样本只能提供探索性证据；小延迟差异不代表统计结论。
- 调用数是模型可见工具次数，不等于浏览器动作次数。Token 包含 cacheRead/cacheWrite；Pi 报告费用不是账单。

## 复现与状态

- 先运行 `scripts/live-refs.mjs --serve`，等九项确定性契约通过；再运行 `benchmarks/pi-agent/compare-refs.py --control ... --output ... --extension ... --chrome ...`。默认六场景、两轮。
- 该比较显式使用模型额度，普通 `make check` 不会启动它。
- 页面事件日志与模型原始记录只保存在本机临时目录；报告只保存脱敏指标与 trace/产物哈希。
- 本轮未修改产品代码，也没有为获胜而替换失败 cell。bro 增强版仍未发布，运行中的安装版未切换。
